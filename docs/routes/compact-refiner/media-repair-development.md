# 依据原文的媒体修复开发

Protocol：`media-repair-development-1.0`。日期：2026-09-14。
状态：完成上下文复核后的有限范围开发准备，不是去臭验证研究或训练数据集。

## 决策与目的

维护者授权决定研究方向，并明确要求改善中文译文。下一项可执行的开发问题是：能否对完整真实文章进行可追踪且有用的修复，同时保留主张、细节、归属、不确定性和行文风格。已有具体阅读缺陷提供了任务，不预设强臭味标签。

使用 `contrast-context-v1` 中三个已暴露的 development 来源：`doc-03`（技术公告）、`doc-05`（读者认为难读但臭味弱的 Cowork 报道）、`doc-04`（明确披露为译文的长访谈）。保留全部原始正文及 hash。这种目的性选样不用于总体或时间效应解释。来源作者身份和翻译方式仍未核实。不打开新的 validation 或 test 材料。

## 候选约定

编辑者接收每篇完整中文正文、本 protocol 和通用编辑目标，不接收私有推理、出现次数分数、复核者缺陷标签、英文原文或预期读者偏好。每个来源保存一个完整文章候选，原输入不变，作为对照。中文原文和候选文本周围的 metadata 说明使用中文，字段名和必要术语保留英文。

允许局部表达或 attachment 修复、依据文章澄清指代、减少可证明冗余的框架，以及重排或拆分已有信息。保留有意义的否定和对比。不得机械替换全部连接词、整体缩短、添加轶事、补充事实，或预设原文主张真实。

具体且实质相关的数字、实体、技术术语、日期、限定、引用、访谈说话轮次、不同示例和独有信息必须保留。不得悄悄解决内部矛盾或缺乏支持的主张，必要时单独记录 `unresolved_content_issues`。内容纠正与风格或结构修复不同，不能隐藏在宣称保留原意的候选中。

记录精确且互不重叠的原文操作，包含 `operation_id`、`start_char`、`end_char`、`before`、`after`、`operation_type`、`reason` 和 `preservation_notes`；offset 按原始正文 Unicode code point 计算。从右向左重放操作，必须精确复现候选。每个来源都有完整 `output.txt` 和 `operations.json`，包含原文及输出 hash、可用时的角色或模型身份，以及未解决问题。若没有原文支持的修复，可以返回不变结果。

## 检查与复核

主 agent 验证不可变原文 hash、操作边界、非重叠性、before 精确文本、重放、完整输出 hash 和清单差异。字面变化检查是诊断，不是语义保留证明。随后由独立助手通读原文与输出，审查增删命题，包括归属、否定、数值范围和遗漏细节。分别保留失败、不确定性和改进提议；绝不通过覆盖失败候选抹除历史。

助手判定保留检查通过，仍只是助手判断，不产生人工接受、偏好率、臭味强度、SFT 导出或训练资格。之后若有理由开展读者比较，应使用整篇文章上下文和相同呈现方式，区分可读性与感知臭味。不要再把大量细微修改作为强臭味标注任务发送。

## 输出与限制

私有根目录：`data/local/media-repair-development-v1/`。编辑前记录原文和 protocol hash，之后记录编辑者与复核者产物。不需要外部 API、模型下载、本地或云训练、GPU。这是当前助手的工程或开发提案；可复现性体现在原文身份和操作重放，不保证文本生成具有确定性。

在已复核数据覆盖、译文输入评估、使用权及实际模型工作负载足以支持训练前，不得训练。后续独立抽样保留译文分层和零信号案例，匹配来源、体裁和主题，并单独冻结分析计划。
