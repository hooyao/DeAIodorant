# DeAIodorant Refinement Roadmap

## North star

DeAIodorant takes a generated Chinese draft and returns a version that readers
prefer to read while preserving the draft's intended meaning, facts,
qualifications, and useful detail.

The product does not determine whether text was generated by AI. It does not
optimize for AI-detector evasion. A text can be generated by AI and already be
good; a human text can contain the same irritating patterns. The product acts
only on editing problems that reduce reader experience.

## Operational definition of “AI smell”

A pattern is a product-relevant smell only when all three conditions hold:

1. it can be located or measured consistently;
2. removing or changing it improves blinded reader preference;
3. the edit does not damage meaning, facts, fluency, or the intended voice.

A corpus difference is only a hypothesis source. If a feature differs between
pre and post cohorts but readers do not prefer the intervention, it is not a
refinement target.

## Starting point

### Available assets

- a 30-document pilot corpus: 10 pre-period InfoQ, 10 post-period InfoQ, and 10
  pre-period Machine Heart documents;
- known contamination and source imbalance in the pilot corpus;
- a larger prepared corpus being built independently on a DGX Spark;
- deterministic translation filtering and its exposed benchmark history;
- 150 dense numeric Chinese-text features;
- cohort-blind sparse character, POS, function-word, punctuation, opening, and
  dependency-pattern features;
- fixed Stanza Chinese tokenization, POS, lemma, and dependency annotation;
- monthly metadata and content fingerprints.

### Available hardware

| Hardware | Best use |
|---|---|
| Current 8 GB GPU machine | feature extraction, rules, small quantized models, CLI development |
| RTX 4080 16 GB | 7B–14B quantized inference, candidate generation, small QLoRA experiments |
| DGX Spark 128 GB unified memory, approximately 270 GB/s bandwidth | batched 14B–32B inference, teacher generation, larger LoRA experiments, corpus-scale jobs |
| CPU | Stanza parsing, deterministic guards, diffs, entity/number checks, statistics |

The DGX Spark can fit large models, but its memory bandwidth makes very large
autoregressive decoding relatively slow. It is more valuable for batched
offline generation and training than for choosing the largest possible online
model.

### Missing assets

- no validated taxonomy of reader-disliked Chinese writing patterns;
- no paired generated-draft to accepted-edit dataset;
- no blinded reader-preference benchmark;
- no human-edited upper-bound examples;
- no span-level record of which edits caused an improvement;
- no refinement engine;
- no meaning-preservation benchmark for edits.

The missing evaluation data is more important than collecting another feature
family or selecting a larger model.

## The three separate problems

### 1. Candidate discovery

Find patterns that may explain why generated Chinese feels repetitive,
generic, over-structured, or tiring. Corpus features, sparse patterns,
qualitative reading, and editor annotations all contribute candidates.

Output: a versioned smell hypothesis catalog, not product rules.

### 2. Causal edit validation

Change one pattern at a time while preserving the rest of a passage. Use
blinded reader comparisons to determine whether that edit improves the text.

Output: validated edit operations with positive examples, counterexamples, and
failure conditions.

### 3. Refinement

Apply only validated edits to new drafts, preserve locked content, and return an
inspectable diff.

Output: the DeAIodorant product.

## Candidate smell taxonomy

This taxonomy is deliberately provisional. Each category must survive causal
edit validation.

| Category | Candidate symptoms | Possible edit operations |
|---|---|---|
| Generic framing | broad era statements, empty importance claims, context that adds no information | delete, replace with concrete context |
| Excessive signposting | repeated “first/second/finally,” summary announcements, metadiscourse | remove, merge, retain only necessary navigation |
| Restatement | conclusion repeats introduction, adjacent sentences paraphrase the same claim | delete duplicate proposition, consolidate |
| Uniform rhythm | similar sentence length, paragraph length, and clause structure throughout | split, merge, vary construction where justified |
| List overuse | every idea forced into symmetric numbered bullets | convert selected items to prose or an asymmetric structure |
| Formulaic symmetry | repeated parallel triples, “not only...but also,” balanced slogans | rewrite only when the symmetry carries no rhetorical value |
| Abstractness | dense abstract nouns, generic benefits, few actors or observable actions | restore concrete subject, action, constraint, or example from available facts |
| Over-explanation | obvious concepts explained repeatedly, excessive transitions between simple points | compress or delete |
| Flat stance | uniformly neutral, no prioritization, all points presented as equally important | restore emphasis supported by the source |
| Unjustified certainty | absolute conclusions unsupported by the input | restore qualification and modality |
| Synthetic intimacy | fabricated personal experience, fake empathy, or invented authorial authority | remove rather than fabricate a “human” voice |
| Canned ending | generic future outlook or motivational close disconnected from the article | end on the final substantive point |

The system must not invent anecdotes, concrete details, opinions, citations, or
personal experience merely to make text sound human.

## Evaluation contract

Evaluation must exist before choosing the final refinement architecture.

### Primary metric

Blinded pairwise reader preference:

> Which version would you rather continue reading?

This question directly measures the product objective and avoids asking raters
to guess authorship.

### Secondary reader ratings

- naturalness;
- clarity;
- specificity;
- redundancy;
- formulaic structure;
- preservation of the intended voice.

### Preservation gates

- named entities unchanged unless explicitly editable;
- numbers, units, dates, and citations preserved;
- negation and modality preserved;
- key propositions retained;
- no new factual claims;
- no invented personal experience or authority;
- acceptable grammar and referential coherence.

Deterministic checks should run first. A separate NLI or semantic model may be
tested later as an additional warning signal, but it cannot be the sole
preservation gate.

### Operational metrics

- edit distance and percentage of text changed;
- latency and throughput;
- model memory and total compute;
- percentage of edits accepted or reverted;
- failure and fallback rate.

### Baselines

Every experiment includes:

1. unchanged input;
2. simple deterministic rules;
3. one prompt-only local-model rewrite;
4. human edit for a small upper-bound subset.

Feature distance to the pre-period corpus is diagnostic only and never the
primary score.

## Route A: Deterministic editing rules

### Method

Use parsers, lexicons, repetition detection, and structural measurements to
locate explicit problems. Apply bounded operations such as deleting duplicate
transitions, collapsing repeated conclusions, or removing generic openings.

### Strengths

- cheap and fast;
- deterministic and inspectable;
- low hallucination risk;
- works on the 8 GB machine;
- useful as a baseline and as final-product guardrails.

### Weaknesses

- brittle around context and rhetoric;
- difficult to rewrite abstract sentences naturally;
- can remove intentional repetition or structure;
- rule count grows quickly.

### Minimum experiment

Implement five high-precision rules against 20 passages. Require every edit to
produce a diff and reason code. Compare rule output with unchanged input.

### Continue when

Rules improve preference without meaning failures and have low false-positive
rates.

### Stop expanding when

Most remaining problems require contextual rewriting rather than safe
deletion, merging, or substitution.

## Route B: Feature-distance optimization

### Method

Generate bounded candidate edits and prefer candidates that move validated
features toward a target range while satisfying preservation constraints.

### Strengths

- connects measurements to controllable edits;
- transparent;
- can balance several style properties;
- does not require a learned preference model initially.

### Weaknesses

- matching human-corpus distributions does not guarantee reader preference;
- global feature targets can erase genre or author voice;
- feature gaming is easy.

### Minimum experiment

Use only features already validated by reader interventions. Compare feature-
guided selection with random candidate selection.

### Role in final product

Controller and diagnostic, not the sole quality objective.

## Route C: Prompt-only local LLM rewrite

### Method

Send the complete draft, locked facts, desired intensity, and a concise editing
instruction to a Chinese-strong instruct model.

### Strengths

- fastest way to obtain a strong qualitative baseline;
- handles context and fluent rewriting;
- requires no paired training data;
- easy to compare across 4B, 7B, 14B, and 32B sizes.

### Weaknesses

- can rewrite too much;
- may fabricate details or flatten voice;
- prompt and model behavior are inconsistent;
- difficult to attribute improvements to particular operations.

### Minimum experiment

Use 20 passages and one frozen prompt. Generate one low-temperature candidate
per model size. Blind model identity during rating.

### Hardware

- 3B–4B quantized baseline on the 8 GB machine;
- 7B–14B quantized models on the RTX 4080;
- 14B–32B batched models on the DGX Spark.

### Role in final product

Baseline, teacher, or optional high-quality backend. Prompt-only full-document
rewriting is unlikely to provide enough control by itself.

## Route D: Analyze, plan, and locally rewrite

### Method

1. deterministic analysis locates candidate spans;
2. an edit planner selects allowed operations;
3. a local model rewrites only those spans with limited context;
4. deterministic preservation checks accept or revert each operation;
5. the product returns a structured diff.

### Strengths

- preserves more of the original voice;
- reduces hallucination surface;
- explains every edit;
- supports low, medium, and high intensity;
- combines the strongest parts of rules and language models.

### Weaknesses

- more engineering than one-shot rewriting;
- local edits can damage cross-sentence coherence;
- edit planning requires a validated taxonomy.

### Minimum experiment

Choose three validated smell categories. Run targeted rewrites on the same 20
passages used by Routes A and C.

### Role in final product

Recommended first MVP architecture.

## Route E: Candidate generation and constrained reranking

### Method

Generate several alternatives for each targeted span or document. Reject
candidates that fail preservation checks, then rank survivors using:

- validated feature changes;
- edit size;
- repetition and fluency checks;
- eventually, a small human-preference model.

### Strengths

- improves reliability without immediately training the generator;
- separates generation from selection;
- allows safe fallback to the original;
- batching maps well to the DGX Spark.

### Weaknesses

- multiplies inference cost;
- a weak ranker selects polished but semantically wrong candidates;
- requires careful diversity control.

### Minimum experiment

Generate four candidates per passage from one model. Compare random candidate,
feature-ranked candidate, and human-selected candidate.

### Role in final product

Likely second stage after the targeted-rewrite MVP.

## Route F: Supervised edit model

### Method

Train a model on generated draft to accepted human edit pairs. Options include:

- LoRA or QLoRA adaptation of a 3B–14B instruct model;
- an encoder-decoder Chinese edit model;
- operation-conditioned examples such as delete, merge, split, concretize, or
  reduce signposting.

### Strengths

- consistent editing policy;
- lower prompt complexity;
- lower production latency than a large general model;
- can learn house style and refinement intensity.

### Weaknesses

- requires high-quality paired edits;
- noisy synthetic targets teach new artifacts;
- full rewrites can still lose meaning;
- model updates require a stable evaluation suite.

### Minimum data

Start only after several hundred accepted edit pairs. Thousands of diverse,
editor-reviewed pairs are preferable.

### Hardware

- QLoRA for small models on the RTX 4080;
- batched LoRA or QLoRA for larger models on the DGX Spark.

### Role in final product

Strong long-term candidate after the product has collected real accepted edits.

## Route G: Preference optimization

### Method

Collect preferred and rejected refinements for the same input, then use:

- direct preference optimization;
- a small pairwise reward model;
- reranker training;
- preference-weighted supervised training.

### Strengths

- aligns directly with reader preference;
- captures tradeoffs difficult to encode as rules;
- rejected candidates are valuable training data.

### Weaknesses

- preferences vary by audience and genre;
- annotation inconsistency can dominate;
- reward hacking and over-editing are possible;
- substantially more complex than supervised editing.

### Minimum data

Do not begin with the current corpus. Begin after the product has at least
hundreds, preferably thousands, of blinded or real-user preference pairs.

### Role in final product

Later optimization layer, not the starting route.

## Route H: Edit tagging and operation prediction

### Method

Train a small model to mark spans and predict operations such as keep, delete,
merge, split, soften, or rewrite. A separate generator handles only rewrite
operations.

### Strengths

- cheap inference;
- explicit edit boundaries;
- easier to audit than full generation;
- compatible with deterministic rules.

### Weaknesses

- requires span-level annotation;
- tag boundaries can be ambiguous;
- a tagger alone cannot produce fluent replacements.

### Minimum experiment

Manually annotate 100 passages with span and operation labels, then measure
agreement before training.

### Role in final product

Promising compact planner for the hybrid architecture.

## Route I: Teacher generation and distillation

### Method

Use a strong 14B–32B offline teacher to propose multiple edits. Human editors
accept, reject, or correct them. Distill accepted behavior into a smaller
production model.

### Strengths

- uses DGX Spark capacity offline;
- creates training data faster than editing from scratch;
- production model can fit 8–16 GB hardware.

### Weaknesses

- teacher artifacts propagate into the student;
- unreviewed synthetic pairs are unsafe;
- teacher quality does not replace reader evaluation.

### Minimum experiment

Compare editing time from scratch with review-and-correct time on 50 passages.
Continue only if teacher assistance saves editor time without lowering quality.

### Role in final product

Efficient data flywheel after a validated editing policy exists.

## Route J: Retrieval-conditioned refinement

### Method

Retrieve high-quality human examples from the same genre and use their
structural properties or short style demonstrations to condition editing.

### Strengths

- genre-aware;
- can preserve different editorial styles;
- reduces reliance on one universal style prompt.

### Weaknesses

- copying and copyright risks;
- retrieval can inject topic content;
- poor matches distort voice;
- requires strict overlap detection.

### Minimum experiment

Compare no retrieval, source-matched structural guidance, and full-text
demonstrations. Reject the route if phrase copying increases.

### Role in final product

Optional genre adapter, not a core requirement.

## Route K: Generation-time integration

### Method

Apply validated style controls while the original article is generated rather
than as a post-processing step. This can include system instructions, style
tokens, decoding penalties, or a refinement pass inside the generation
workflow.

### Strengths

- avoids rewriting an already poor draft;
- can reduce latency and edit distance;
- useful for integrated publishing tools.

### Weaknesses

- couples DeAIodorant to the generation model;
- cannot refine externally generated text;
- harder to maintain a model-independent product.

### Role in final product

Integration option after the standalone refinement layer works.

## Route L: Human-in-the-loop editing

### Method

Present suggested edits individually with reason codes, accept/reject controls,
and intensity settings.

### Strengths

- highest safety;
- produces real preference and edit-pair data;
- respects author voice;
- enables immediate product value before full automation.

### Weaknesses

- requires interaction;
- acceptance behavior can be noisy;
- UI and workflow design matter.

### Role in final product

Recommended initial interface and the main data flywheel.

## Recommended convergence path

The routes are complementary rather than mutually exclusive.

~~~text
high-precision rules
    + targeted local-model rewriting
    + deterministic preservation gates
    + candidate reranking
    + inspectable human accept/reject workflow
    -> accepted edit and preference dataset
    -> supervised compact refiner
    -> optional preference optimization and distillation
~~~

The recommended MVP is Route D with Route A guards. Route E follows if multiple
candidates materially improve reliability. Routes F, G, H, and I begin only
after the product generates trustworthy paired data.

## Small experiments in order

### Experiment 0: Reader benchmark

Use 20 passages of 500–1,000 Chinese characters across at least three genres.
Include current post-period InfoQ passages only as exploratory inputs, not as
ground-truth AI labels.

Produce:

- unchanged input;
- a human edit for 5–10 passages;
- locked facts and entities for preservation checking;
- blinded reader-preference forms.

Exit condition: raters can distinguish meaningful quality improvements and the
rating questions are understandable.

Current exploratory checkpoint: 10 low-burden passage ratings and three
blinded pairwise interventions have been completed. Two contrast-reduction
variants were preferred, while one aggressive compression failed. The reader
question is usable, but the sample is too small and the revisions exposed a
new preservation requirement: retain explicit grammatical arguments and avoid
flattening the text into a cold, uniformly compressed voice. See
[Research Progress](research-progress.md).

### Experiment 1: High-precision rules

Test five operations:

- remove empty generic openings;
- reduce repeated signposting;
- delete adjacent restatements;
- remove disconnected canned endings;
- collapse unnecessary list structure.

Exit condition: identify which operations have low false-positive rates and
positive reader preference.

### Experiment 2: Prompt-only baseline

Run one frozen prompt on small, medium, and larger local model sizes. Keep
temperature and input constant.

Exit condition: establish the best quality, latency, and preservation baseline
available without training.

### Experiment 3: Targeted hybrid

Use validated detectors to request local span edits instead of full rewrites.
Accept or revert each edit independently.

Exit condition: outperform prompt-only rewriting on preference or preservation
at comparable cost.

### Experiment 4: Candidate reranking

Generate four candidates only for spans that need contextual rewriting.

Exit condition: automatic ranking approaches human candidate selection without
increasing preservation failures.

### Experiment 5: Human-in-the-loop pilot

Expose reason-coded edits and record accept, reject, modify, and revert events.

Exit condition: users obtain value and the event data is reliable enough to
build paired examples.

### Experiment 6: Supervised compact model

Train only after enough accepted edit pairs exist.

Exit condition: match or exceed the hybrid teacher at lower latency and cost.

### Experiment 7: Preference optimization or distillation

Choose this only when supervised learning plateaus and sufficient preference
data exists.

## Decision rules

- If deterministic rules provide a large fraction of the preference gain, keep
  them as first-class operations rather than replacing them with a model.
- If full-document rewriting improves style but loses meaning, move immediately
  to targeted editing.
- If multiple candidates create substantial gains, invest in reranking.
- If preferences differ strongly by genre, build genre policies rather than
  one global “human style.”
- If accepted edit pairs remain scarce, do not fine-tune.
- If a larger model adds little reader preference, deploy the smaller model.
- If feature changes do not predict reader preference, remove them from the
  product objective even if they separate corpora.
- If an edit cannot pass preservation gates, return the original span.

## What not to do next

- do not train a human-versus-AI classifier;
- do not optimize against an AI detector;
- do not assume every pre/post corpus difference is undesirable;
- do not train on raw pre-period articles as unpaired rewrite targets;
- do not use an unreviewed strong model to generate thousands of “gold” edits;
- do not select the largest model before establishing the reader benchmark;
- do not rewrite complete documents when only a few spans are problematic;
- do not add more feature families until existing features are connected to
  reader-validated edit operations.
